# 色収差サンプリング軽量化（2026-09-09）

PR #2 の `46301959842272329365f40d97af23d746a6952b` を起点とした追加実装。

## YMM4での変更

- 標準モードでもスペクトル重み・正規化をC#で事前計算。1画素・1タップにつき3回あった指数関数、重み累積、最後のRGB除算を除去。重みテーブルはステップ数/品質変更時だけ再構築。
- 光の方向、しきい値の換算、コントラスト逆数もCPU側で計算。
- 「色収差の品質 → 軽量（最大8サンプル）」を追加。128→8で色収差のテクスチャ参照回数は16分の1。**エフェクト全体のGPU速度が16倍になるという意味ではない**。
- 元の各スペクトル重みを隣接する8点に線形配分し、RGB各チャンネルの総重量と一次モーメントを保持。一定色・線形ランプの積分を保持するが、細かい模様は近似誤差が出る。
- 標準を既定値として既存プロジェクトの見た目を維持。3〜8ステップは軽量でも元と同等。
- 虹色0かつ変位強度0（または既存仕様で色収差0）の合成出力は入力を直接返し、グラフ全体の評価を省略。流れ可視化では虹色のためだけのノイズ計算を省略。

## 検証

- Python 24テスト：重み、全3〜128ステップの総重量/一次モーメント、出力の有限性・範囲・再現性、既存数学テスト。
- 起点コミットと新標準モードの小規模ランダム画像比較（3/8/16/128ステップ）で最大絶対差6.56e-7。浮動小数点の丸め順による差を許容し、ビット一致は主張しない。
- C#のテストは製品のSpectralTable.csそのものをリンクし、2048バイト配置、重みと総重量/一次モーメントを検査。Windows CIはDLL/ps_4_0コンパイルと定数バッファのオフセットも確認。
- 実GPUの処理時間と実画像/動画の見た目は別途YMM4上で確認が必要。既存のCPU参照実装はGaussianBlurやアルファ処理・時間単位がGPUと完全一致していないため、この画質指標をGPUの画質保証としては扱わない。
